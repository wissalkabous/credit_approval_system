01
Introduction

This project is a bank credit approval system built in Python. It goes beyond simply running an ML model — it applies software engineering best practices to produce maintainable, extensible, and testable code.

Main Objective
Predict whether a bank customer will be approved or rejected for a loan, based on 12 financial features.
Technical Objective
Apply OOP, DIP, Design Patterns, Async programming, and expose everything via a modern REST API with FastAPI.
Result
Complete web application: HTML form → ML prediction → JSON response + visual interface with animated gauge.
Project philosophy: every component depends on an abstract interface, never on a concrete implementation. Changing the ML algorithm, the logging system, or the storage layer requires no changes to other modules.

03
Problem Statement

Building an ML system without a rigorous architecture creates several serious issues in production:

Problem 1 — Tight Coupling
If train.py directly instantiates RandomForestClassifier(), changing the algorithm forces modifications in every file that uses it. The code becomes brittle.
Problem 2 — Untestable Code
Without interfaces, it is impossible to replace the real ML model with a mock in unit tests. Every test requires a full model training — slow and expensive.
Problem 3 — Code Repetition (DRY Violation)
Logging the start/end of every method, measuring execution times, validating inputs — writing this manually in every function produces hundreds of duplicated lines.
Problem 4 — No API Data Validation
Without validation, a user can send age: "thirty" or credit_score: 9999 to the API → a cryptic error inside the ML model with no clear message.
Problem 5 — Blocking Server
Without async, each request blocks the server until fully completed. If 100 clients send requests simultaneously, 99 wait in a queue.
# Code WITHOUT proper architecture (to avoid)
def predict(data):
    model = RandomForestClassifier()   # direct dependency, not testable
    model.fit(X_train, y_train)          # re-trains on every call!
    print("Starting predict...")         # manual log repeated everywhere
    return model.predict(data)           # no validation, no error handling

Solution

The project applies 7 complementary methods to address each identified problem.

4.1 — Abstract Classes (ABC)

An abstract class defines a mandatory contract — what a class must do, without dictating how. Any subclass that forgets to implement a method raises a TypeError at instantiation.

# src/interfaces.py — 5 abstract interfaces
from abc import ABC, abstractmethod

class IModel(ABC):
    @abstractmethod
    def train(self, X_train, y_train) -> None: pass
    @abstractmethod
    def predict(self, X) -> np.ndarray: pass
    @abstractmethod
    def save(self, filepath: str) -> None: pass

# src/model.py — concrete implementation
class CreditModel(IModel):        # inherits from IModel
    def train(self, X_train, y_train):
        self.model.fit(X_train, y_train)   # real implementation

# Missing a method? Python raises: TypeError: Can't instantiate abstract class

4.2 — Dependency Inversion Principle (DIP)

The D in SOLID: high-level modules must not depend on low-level modules — both must depend on abstractions.

Without DIP
CreditModel creates ConsoleLogger() directly → impossible to change the logger without modifying CreditModel.
With DIP
CreditModel receives an ILogger as parameter → inject any logger without touching the class.
# src/model.py — DIP: depends on interfaces, not concrete classes
class CreditModel(IModel):
    def __init__(self,
                 logger:     ILogger     = None,   # interface, not ConsoleLogger
                 repository: IRepository = None):  # interface, not ModelRepository
        self.logger     = logger     or ConsoleLogger()
        self.repository = repository or ModelRepository()
Test benefit: In unit tests, inject a MockLogger that collects messages instead of printing them — no changes needed in production code.
4.3 — Design Pattern: Singleton

The Singleton ensures a class has only one instance throughout the entire application lifetime, with a global access point. Applied to the DIContainer.

# src/container.py — Singleton Pattern via __new__
class DIContainer:
    _instance = None   # class variable — holds the unique instance

    def __new__(cls):
        """Singleton: always returns the same instance."""
        if cls._instance is None:
            cls._instance = super().__new__(cls)   # created only once
        return cls._instance                        # same object every time

    def __init__(self):
        if hasattr(self, '_initialized'): return  # prevent re-initialization
        self._services = {}
        self._register_defaults()
        self._initialized = True

# Proof of uniqueness
c1 = DIContainer()
c2 = DIContainer()
print(c1 is c2)          # → True  (same object in memory)
print(id(c1) == id(c2)) # → True  (same memory address)
Why Singleton here? The DIContainer registers all services (logger, repository). Without Singleton, every module would create its own container with a different logger → inconsistency. The Singleton guarantees one shared logger across the entire application.
4.4 — IoC Container (Inversion of Control)

The DIContainer is a centralized factory. It creates objects and automatically injects their dependencies — no need to manually wire each object with its parameters.

# src/container.py — built-in Factory Method
def create_model(self, model_type="random_forest") -> IModel:
    logger     = self.get_service('logger')
    repository = self.get_service('repository')
    return CreditModel(model_type, logger, repository)  # auto injection

# train.py — clean usage
container = initialize_container()
model     = container.create_model(model_type="random_forest")
processor = container.create_data_processor("data/raw/credit_data.csv")
predictor = container.create_predictor(model, processor)
# ConsoleLogger and ModelRepository are injected automatically
4.5 — Python Decorators

A decorator is a function that wraps another function to add behavior without modifying its code (Open/Closed Principle).

# src/decorators.py
def timing(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start  = time.time()
        result = func(*args, **kwargs)
        print(f"[TIME] {func.__name__} : {time.time()-start:.3f}s")
        return result
    return wrapper

# src/model.py — applying decorators
def train(self, X_train, y_train):
    @log_execution   # prints [RUN] _train  /  [OK] _train
    @timing          # prints [TIME] _train : 1.24s
    def _train():
        self.model.fit(X_train, y_train)
    return _train()

4.7 — Asynchronous Programming (async / await)

FastAPI is built on asyncio. Routes declared as async def do not block the server. BackgroundTasks run operations after the response has been sent to the client.

# api/main.py — Async Background Task
async def log_prediction_async(statut: str, confiance: str, risque: str):
    """Background log — response is already sent to the client."""
    await asyncio.sleep(0)   # yield to the event loop
    print(f"[ASYNC LOG] {statut} | {confiance} | {risque}")

@app.post("/api/predict")
async def predict(data: PredictionInput, background_tasks: BackgroundTasks):
    # ... ML prediction ...
    background_tasks.add_task(log_prediction_async, statut, confiance, risque)
    return result   # ← response sent immediately

06
Conclusion

This project demonstrates that a production ML system goes far beyond model.fit() — it requires a rigorous software architecture to be maintainable, testable, and extensible.

ABC + DIP

5 abstract interfaces (IModel, ILogger...) enforce implementation contracts and allow replacing any component without breaking others.

Singleton Pattern

The DIContainer guarantees a single instance across the application — one shared logger, one repository, consistent configuration.

Decorators

@timing and @log_execution add logging and performance tracking without duplicating code — DRY and Open/Closed principles respected.

FastAPI + Async

async def non-blocking routes and BackgroundTasks allow the server to handle many simultaneous requests without waiting for each to finish.
